- Verdict (Phase 2, SGLang Diffusion 0.5.19, Z-Image-Turbo, 2x L40S, --sp-degree 2 --ulysses-degree 2): **GO by the stated criteria.** T_detect at defaults = 600.2 s for both case A (kill -9) and case B (SIGSTOP), 3 runs each (range 600.21-600.28). Floor on the only configurable detection knob (--scheduler-rpc-timeout, request-level): 30 s clean, 10 s cut 27/230 healthy requests (12% false positives) -> floor 30 s >= 10 s.
- A == B: the surviving rank waits inside the SP all-to-all, so a dead peer and a stopped peer look identical; the only thing that fires is torch's ProcessGroupNCCL op timeout at its DEFAULT 600 s on the SP subgroup (PG ID 2, ALLTOALL_BASE). --dist-timeout 3600 applies to the default group only and did not change this. Nothing in the diffusion stack polls worker liveness after startup.
- No eviction: after the timeout the worker aborts (~60 s later), but the HTTP server keeps /health=200 and keeps queueing requests indefinitely (no_self_teardown in 6/6 runs; 234-235 requests lost per run in the 600 s window). The 1-step probe only "detected" via its own 60 s client timeout (59 s), because it queues behind the hung request.
- /health never left 200 in any run (readiness flag only); /liveness likewise.
- Per-step durations are stable and linear in pixels: 256^2 43 ms, 512^2 66 ms, 1024^2 222 ms, 1536^2 533 ms (p99 ~ max). A per-step watchdog, if one existed, would have a warm global floor of 1.07 s (2x safety) but a per-shape floor from 0.14 to 1.07 s (8x spread); one global value is 8x slack on small shapes. Cold-shape first steps were seen at 5.4 s (512^2, calibration run), which such a watchdog would also have to tolerate.
- IPC all-to-all path (SGLANG_DIFFUSION_IPC_A2A=true, default) is unusable on this host: the first request hung in the first step, the 10 s IPC timeout never fired, torch's heartbeat monitor killed the worker after 480 s, and the HTTP server served /health=200 for the next ~2 h with dead workers. All measurements use SGLANG_DIFFUSION_IPC_A2A=false (NCCL via SHM, NCCL_P2P_DISABLE=1); the IPC-path timeout is therefore unmeasured here.
- Deviations from the cookbook: the Z-Image-Turbo NVIDIA recipe is single-GPU; this experiment uses the documented --sp-degree/--ulysses-degree flags at 2 to force a per-step collective between ranks. Steps fixed at the model's 9 (LOAD_ARGS="--steps 9,9,9"); rate 0.376 req/s (70% of 0.537 saturation); harsh profile not run (1536^2 already in mixed).
- Phase 2b characterization (Z-Image-Turbo 256^2..1536^2 @9 steps; Wan2.2-TI2V-5B 480p/704p x 17/49/81 frames @9 steps, SP=2, SGLANG_DIFFUSION_IPC_A2A=false): denoising-step time is a tight, near-deterministic function of shape (p99.9 within 1-2% of p50): image 43-532 ms, video 167-712 ms at 480p, linear in frame count (~8.7 ms/frame at 480p).
- The largest execution quantum of a video request is NOT a denoising step but the VAE decode: 1.2 / 3.6 / 6.0 s at 480p for 17/49/81 frames and ~12.8 s at 704p x 81 (first-request cold 7.0 s at 480p x 17). For images the largest quantum is text encoding (0.27-0.44 s) at small shapes and decode (0.9 s) at 1536^2.
- Static-timeout cost: one global deadline safe for every served workload is D_global = 25.6 s (2 x largest warm quantum, 704p x 81 decode), 31 s including cold starts; the smallest workload needs 0.54 s (Z-Image 512^2) -> 48x slack, >25 s absolute. A per-stage static table (decode / step / encode) still carries 10x shape-dependence inside the decode stage and 16x inside the step.
- Cold starts are a first-request-after-launch effect (3.0-3.6 s first step, 7 s first decode, 1.7 s first text encode), not a per-shape effect: a new shape's first step equals its warm step; 120 s idle adds nothing.
- Method notes: both Wan runs used 9 steps (LOAD_ARGS leaked from the Z-Image setup); the 704p shapes were served by the still-running 480p/conc4 server (port collision), so their records live in that run's logs and their 'cold' category is first_of_shape. 1280x720 fails under SP=2 (latent height 45 is odd); 1280x704 is the SP-2-compatible 720p. Launchers now refuse to start when the port already answers.
- Phase 3a resume-state inventory (boundary after step 2, both ranks): Z-Image shards latents spatially across SP ranks (checksums differ; 0.06-0.56 MiB per rank), so recovery needs the peer's shard; Wan2.2-5B keeps the loop-level latent replicated on every rank at all tested shapes, including 85 frames, because Wan pipelines auto-enable enable_sequence_shard (DiT-internal sharding, sampling_params.py), so a surviving rank already holds the full x_t.
- State composition is dominated by the solver and conditioning, not the latent: 704p x 81 -> latent 13.5 MiB (48 ch, fp32), UniPC history (2 model_outputs + last_sample) 40.6 MiB, prompt embeddings 16 MiB, total S_state 70 MiB; 512^2 image on Wan -> 16.8 MiB of which 16 MiB is conditioning. Conditioning is per-request static (protect once at admission); per-step dynamic state is latent + solver history (<= 54 MiB here). Euler models (Z-Image) carry no history.
- Checkpoint cost on the serving rank: device->pinned host copy of the full bundle 22 ms at 704p x 81 (1.1% of the 2.0 s step), 2-10 ms for 480p video, 0.14-0.19 ms for images (<0.3% of step); torch.save 0.8-64 ms. Every-boundary protection is affordable at every workload measured; no checkpoint-frequency trade-off emerges from this data.
- Resume correctness caveat: multi-step solvers (UniPC) need their history to resume bit-exactly; the earlier bit-exact result was Euler. Phase 3b must measure resume with history carried vs. lower-order restart.
- Phase 3c containment (Wan2.2-5B, SP=2, peer SIGSTOPped, probe deadline 10 s after last quantum): torch.distributed._abort_process_group (ncclCommAbort) called from a side thread NEVER returned; with a 650 s observation window the rank died only via torch's own path (SP-group NCCL op timeout at +600 s, then +60 s watchdog-thread terminate), exactly as without the abort. TORCH_NCCL_ASYNC_ERROR_HANDLING=0 made no difference. In-process abort buys nothing.
- TORCH_NCCL_USE_COMM_NONBLOCKING=1 is unusable with this stack: every denoising step fails with 'NCCL Error 7: operation in progress' even without a fault (the all-to-all path does not poll non-blocking communicators).
- Exiting the surviving rank at the deadline (FT_ABORT_MODE=exit) is the only bounded primitive: process gone 0.1-8 s after os._exit (CUDA context teardown), all later requests fail in 0 s (rank-0 ZMQ endpoint vanished) instead of hanging; /health stays 200 and nothing restarts the rank. Containment cost = deadline + context teardown; recovery cost = rank restart with model reload (37 s for the 5B here).
- Measurement note: earlier '~70 s rank death' readings in containment_B were our own stop.py teardown (POST_GRACE=60); the analyzer now cuts at the first stop event. Video-job polling raced uvicorn keep-alive expiry ('Server disconnected without sending a response') and inflated pre-injection error counts in video runs; the generator now closes connections per video request.
- Phase 3b-1 trajectory portability (SP=2 state after step 3 -> fresh SP=1 process, 9 steps, fixed seed): GO on both solver families. Z-Image/Euler: resumed final latents differ from the SP=1 reference by rel-L2 2.04e-2, identical to the SP2<->SP1 control (2.04e-2); SP=1 run-to-run is bit-exact. Wan2.2-5B/UniPC: full-history resume rel-L2 8.99e-2 vs control 9.02e-2 (no resume-induced error); low-order restart 1.03e-1 (+15%). Restore cost 2-18 ms from a 0.5-25 MiB file. Resume requires injecting solver attributes the fresh scheduler has not created yet (UniPC this_order).
- SP2<->SP1 control difference is large for Wan (9% rel-L2 vs 2% for Z-Image); it is a property of the parallel configuration (fp32 latents with bf16 compute, SP-dependent attention path), not of resume, and is reported as the control.
- Rank restart decomposition (startup_decomp.py): spawn + torch/sglang import ~9 s (model-independent), weight load + H2D + device setup 15-17 s (same for Z-Image 6B and Wan 5B), warmup 0.5-2 s (Z-Image) to ~12 s (Wan). Total 24-26 s (Z-Image) / 37-43 s (Wan 5B). B3 would remove all three.
- B3-1 (in-process coexistence, peer SIGSTOPped): the surviving rank's main thread is not inside the collective; it is blocked in an ordinary cuBLAS launch (attention output projection) behind the stuck all-to-all once the context's launch queue is full. A side thread on a fresh CUDA stream cannot launch even an in-place memset on a pre-allocated buffer. In-process continuation (SP2->SP1 in the same process) is impossible on the stock execution path; the whole CUDA context is launch-dead.
- B2 (separate process on the same GPU during the hang): CUDA context init 14 ms (idle 11 ms), bf16 4096^2 matmul 1.07 ms vs 0.51 ms idle (2.1x, GPU time-slices with the spinning NCCL kernel), memset and D2H unchanged, 26.5 GB free of 44.5 GB with the stuck process holding ~18 GB. A fresh process can take over the GPU; the stuck one must be killed to get full throughput back.
- Option-3 probe (bare NCCL, 2 ranks, peer SIGSTOPped, NCCL over SHM): a stuck collective by itself does NOT poison the CUDA context. With nothing issued behind it (async, or synchronous with the current stream waiting on it), a side stream ran 30/30 benchmark iterations at full speed for 30 s. The first kernel launched behind the stuck collective on the dependent stream blocks the calling thread in the driver immediately (not after a queue fills) and takes every other thread's launches with it: this is what B3-1 and the 3c abort hang were. With issuing held back, _abort_process_group returns in ~0.6 s and the main stream is immediately usable (matmul 0.99 ms right after). Conclusion: an issuing discipline (confirm collective completion, under a progress deadline, before issuing further kernels) keeps the process recoverable in place; in-process SP2->SP1 continuation (B3) is feasible in principle. Cost of the discipline (lost CPU/GPU overlap) to be measured next.
